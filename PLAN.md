# PLAN.md — План виконання (порядок розробки)

Операційний план проєкту **Adaptive EvoSim**. Технічні деталі (формули, схеми, контракти) — у `PROJECT_SPEC.md`; цей документ визначає **порядок робіт**. Порядок тут має пріоритет над розділом 14 специфікації.

Логіка порядку: спочатку **конструктор** (щоб одразу можна було створювати істот, перешкоди й хижака та отримати робочі JSON-конфіги), потім **середовище** (фізика в'язкої рідини + живий перегляд, щоб бачити створене в русі), і лише тоді еволюція, хижак та аналітика.

---

## Етап 1 — Каркас проєкту + Конструктор (редактор сутностей)

**Мета:** користувач відкриває UI, збирає істоту, розставляє перешкоди та хижака, зберігає/завантажує JSON. Фізики ще немає.

Задачі:

1. Структура репозиторію за `PROJECT_SPEC.md` §1.1; `pyproject.toml`; порожні модулі з docstring-ами.
2. Docker: `docker-compose.yml`, `backend.Dockerfile`, `frontend.Dockerfile` + `nginx.conf` (проксі `/api`, `/ws`).
3. Backend-мінімум: FastAPI (`main.py`), `schemas.py` — повні Pydantic-моделі `CreatureConfig`, `EnvironmentConfig`, `ExperimentConfig` (§9.1–9.3); ендпоінт `POST /api/creature/validate` з розрахунком `n_joints`, `n_in`, `genome_size`, `creature_hash`; заглушка `GET /api/simulation/status` → `{state:"STOPPED"}`.
4. Frontend-каркас: `index.html` з вкладками Editor / Simulation / Analytics, `theme.css` (токени §10.1), `app.js`, `api.js`.
5. **Конструктор** (`js/editor/*`, §10.2):
   - канвас сцени: сітка, межі світу 60×40, камера (пан/зум);
   - тіло: circle (radius, density) / polygon (3–8 вершин кліками, перевірка опуклості);
   - кінцівки: клік по периметру тіла → точка кріплення; форма сегмента (length, width, density, angle_min, angle_max, motor_torque); до 4 сегментів, до 6 кінцівок; видалення/редагування вибраної;
   - перешкоди: static_polygon / static_circle кліками; moving_polygon — дві точки `p1`,`p2` + period;
   - хижак: waypoint-и кліками, слайдери `v_patrol, v_chase, r_detect, r_aura, r_catch`, радіуси візуалізуються колами;
   - кнопки: **Validate** (через API), збереження кожної сутності у свою бібліотеку, **Use in Experiment**.

**Definition of Done:**
- [ ] `docker compose up --build` → UI на `:8080`, API відповідає.
- [ ] У редакторі зібрано істоту з ≥2 кінцівками (≥2 сегменти кожна), ≥3 перешкоди (включно з 1 рухомою), хижак з ≥3 waypoint-ами.
- [ ] Validate повертає коректні `n_joints / n_in / genome_size`; невалідна конфігурація (напр., 7 кінцівок) показує зрозумілу помилку.
- [ ] Збереження сутності в бібліотеку → завантаження назад повністю її відтворює; файли бібліотек валідні проти `schemas.py`.

## Етап 2 — Середовище (фізика в'язкої рідини) + живий перегляд

**Мета:** створена в конструкторі істота «оживає»: плаває у в'язкому середовищі на тестовій синусоїді моторів, видно це в реальному часі.

Задачі:

1. `config.py` — усі константи (§13). `hydro.py` — чиста математика drag/lift (§2.2): анізотропний опір сегментів, опір круглого тіла, кламп `F_max`.
2. `physics.py` — `pymunk.Space` (g=0, damping), крок `DT=1/120`, застосування гідросил по точках вибірки, кламп `V_MAX`.
3. `creature.py` — побудова Pymunk-тіл/суглобів/моторів із `CreatureConfig`; `obstacles.py` — статичні й кінематичні перешкоди; стіни світу.
4. `world.py` — фасад епізоду: `step()`, `snapshot()`; тестовий контролер-синусоїда (`rate = sin(2πt + фаза_j)·OMEGA_MAX`).
5. Live-канал: `live_stream.py`, WS `/ws/live` (пакети `scene` + `frame`, §9.5), `POST /api/preview {source:"genome"|...}` у спрощеному вигляді «прев'ю сцени з синусоїдою».
6. Frontend: `ws.js` (reconnect, лише останній кадр), `render/renderer.js` + `shapes.js` — рендер тіла, сегментів, перешкод, аури; кнопка **Test swim** у редакторі (поточна сцена → прев'ю).
7. Тести: `test_hydro.py` (анізотропія ≥10×, збіжність обертального опору до аналітики ≤15%, кламп), `test_creature_build.py`.

**Definition of Done:**
- [ ] Тести hydro/build зелені.
- [ ] Демо-істота на синусоїді за 30 сим-с зміщується ≥3 од., без NaN, `|v| ≤ V_MAX` завжди.
- [ ] Headless-швидкість ≥120 000 кроків/с на одному ядрі (≥1000× реального часу).
- [ ] Кнопка **Test swim**: істота з редактора плаває на канвасі ~60 fps, рухомі перешкоди рухаються, обрив WS → автоперепідключення.

> **Відкритий пункт (станом на 2026-10-13).** Усі критерії виконано, окрім
> швидкості: виміряно **~46 000 кроків/с** (≈380× реального часу) замість
> 120 000. Це після 11-кратної оптимізації гарячого шляху; решта впирається в
> стелю Python (`space.step` — 1.5 µs, гідросили — ~11.6 µs, доступ до
> властивостей Pymunk — більшість решти). Дійти до 120 000 можна лише JIT
> (numba) або ядром на C/Rust, а це залежність і ризик для детермінізму, який
> тут важливіший за швидкість.
>
> Нічого не блоковано: покоління етапу 3 (100 × 2 × 30 с = 720 000 кроків) —
> ~16 с на одному ядрі й ~2 с на восьми проти ліміту 60 с.
>
> Критерій **навмисно не переписано** під отриманий результат: підганяти план
> під факт у дипломній роботі не можна. Тег `stage-2` з тієї ж причини не
> поставлено. Повернутись до цієї цифри має сенс **після етапу 4**, коли буде
> відома реальна вартість кроку з raycast-сенсорами та прямим проходом мережі
> (очікуване сповільнення 2–3× лишає ~6 с на покоління на 8 ядрах).

## Етап 3 — Генетичний алгоритм (headless-навчання руху)

**Мета:** істота сама вчиться плавати; прогрес видно по метриках.

Задачі:

1. `brain.py` — MLP `N_in→16→16→N_joints` (§5); `genome.py` — вектор float32, init/crossover/mutate, (де)серіалізація з `creature_hash` (§6.1).
2. `sensors.py` — поки що лише пропріоцепція + осцилятор (радар і аура — етап 4; `N_in` рахується за фактично увімкненими групами).
3. `fitness.py` — компоненти `D`, `Pas`, `E_n` (§7.1); `ga.py` — турнір, елітизм, uniform crossover, гаусова мутація, diversity; `evaluator.py` — multiprocessing.
4. `sim_manager.py` — стани RUNNING/PAUSED/STOPPED, фоновий потік; REST: `start/pause/resume/stop/status`, `GET /api/metrics/generations`; WS `/ws/metrics` (§9.6).
5. `experiment_store.py` (мінімум): `config.json`, append-only `metrics.csv`, `best_genome.json`.
6. UI (Simulation): форма параметрів ГА, Start/Pause/Resume/Stop; `POST /api/preview {source:"best"}` — перегляд найкращого генома. Проста лінія best fitness (повні графіки — етап 5).
7. Тести: `test_genome_ops.py`, `test_determinism.py` (однаковий seed → побітово однаковий `metrics.csv`).

**Definition of Done:**
- [ ] 100 особин × 50 поколінь без помилок; медіана best-fitness поколінь 41–50 ≥ 2× медіани поколінь 1–10.
- [ ] Найкраща особина: чисте зміщення ≥10 од. за 30 с (проти ≈3 у синусоїди).
- [ ] Детермінізм підтверджено тестом; оцінка покоління ≤60 с на 8 ядрах.
- [ ] З UI: старт навчання, пауза/продовження, перегляд найкращої особини наживо без зупинки навчання.

## Етап 4 — Хижак, сенсори, повна фітнес-функція

**Мета:** істоти вчаться виживати — виявляти хижака заздалегідь і уникати його та перешкод.

Задачі:

1. `predator.py` — кінематичний FSM PATROL/CHASE/RETURN (§8.1) за конфігом з конструктора.
2. `sensors.py` — повний вектор: 12 raycast-променів ×2 канали, аура-сенсор `[aura, aura·sin(bear), aura·cos(bear)]` (§4).
3. `fitness.py` — повна формула: `S`, `G_aura`, `C` (collision handler з дебаунсом), термінальна подія «спіймання» (§7.2), усереднення по `E=2` епізодах з різними сідами (§7.3).
4. Live-рендер: промені сенсорів (колір за типом влучання), аура-градієнт, стан хижака в HUD; `source:"live_training"` — трансляція поточного найкращого під час навчання з перемикачем Headless↔Live.
5. Тести: `test_fitness.py` на синтетичних траєкторіях (нерухома → `Pas=1`; у центрі аури → `G_aura≈1`; спіймання на 15 с → `S=0.5`); тест ігнорування власних шейпів променями.

**Definition of Done:**
- [ ] Усі компоненти фітнесу покриті юніт-тестами.
- [ ] Еволюція 100×150: частка спійманих серед топ-10 останнього покоління ≤20% (проти ≥80% у поколінні 1); метрика зберігається.
- [ ] На live-прев'ю видно реакцію: істота змінює курс при появі хижака в зоні сенсорів (підтверджено на ≥3 епізодах).
- [ ] Перемикання Headless↔Live не ламає навчання; просідання темпу ≤20%.

## Етап 5 — Аналітика, збереження експериментів, матеріали для дипломної

**Мета:** повний HUD/Analytics, довготривале зберігання прогонів, експорт CSV/PDF-графіків для роботи.

Задачі:

1. Analytics (повністю, §10.2): Chart.js — Best+Avg Fitness, Diversity, stacked-компоненти фітнесу; реальний час з `/ws/metrics` + відновлення історії з REST після reconnect.
2. HUD (повністю): Gen, таймер, running fitness з розкладом компонентів, стан хижака.
3. `experiment_store.py` (повний формат §11): чекпоінти `gen_NNN.npz` кожні 25 поколінь, відновлення `--resume <run_id>`.
4. Експорт: `csv_export.py`; `plots.py` — matplotlib PNG+PDF (білий фон, підписи українською, dpi=200); `GET /api/experiments`, `GET /api/experiments/{id}/export`; кнопки експорту та таблиця прогонів в UI.
5. `test_api_contracts.py` — усі ендпоінти проти схем §9; crash-safety тест (kill -9 посеред прогону → metrics.csv цілий, чекпоінт читається).
6. README: «від git clone до графіка в дипломі» ≤10 команд; фінальне вичитування відповідності коду ↔ `PROJECT_SPEC.md`.

**Definition of Done:**
- [ ] Повний артефакт прогону на диску; переживає аварійне вбивство процесу.
- [ ] Export CSV валідний; Export PDF — багатосторінковий, друкований стиль.
- [ ] Resume з чекпоінта продовжує криву best fitness без розриву.
- [ ] README перевірено з нуля на чистій машині (Docker-шлях).

## Залежності та порядок

```
Етап 1 (конструктор, схеми)
   └─▶ Етап 2 (середовище: фізика + прев'ю)   ← потребує CreatureConfig/EnvironmentConfig з Е1
         └─▶ Етап 3 (ГА headless)              ← потребує world/hydro з Е2
               └─▶ Етап 4 (хижак, сенсори)     ← потребує ГА-цикл з Е3
                     └─▶ Етап 5 (аналітика, експорт) ← потребує метрики всіх етапів
```

Кожен етап завершується: зелені тести → перевірка DoD → коміт з тегом `stage-N`.
